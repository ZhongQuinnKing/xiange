# 03 引擎链：无数字源时的转谱

## 用什么

1. **SMT**（Sheet Music Transformer，MIT 开源）
   - 代码：github.com/antoniorv6/SMT
   - 权重：PRAIG/smt-fp-grandstaff
   - 该系统为系统级模型，输入宜为单个谱表系统（一行大谱表）
   - 输出 bekern 文本；转 MusicXML 补头 `**kern\t**kern` 后用 music21 解析
2. **oemer**（MIT 开源，独立 venv）
   - 谱图进 → MusicXML 出
3. **Audiveris**（开源，备选）

## 通用要求

- 输入须为印刷谱，清晰度越高越好；**手写谱不做**
- **源分档结论（能力边界）**：高清印刷源全链稳定；屏幕翻拍、压缩视频等低清源会出现可感知的质量下降，个别行可能直接识别失败。同曲有多个源时优先高清印刷源；遇低清源先换源，不硬跑。
- 识别失败的行（低清源常见于个别行）如实告知用户，不硬凑
- 引擎输出一律进 04 质量体系把关，通过才交付
- 无 tempo 标记等细节按 02 的三件套验证处理

## 共识融合（多引擎协同）

单引擎不足时，用两个引擎交叉：逐小节取**共识音高类**（两引擎都读到的＝高置信，直接可用）
＋列出**待裁清单**（只有一家读到的＝逐处核，核一处标一处）。

工具：`tools/consensus.py`（引擎A 出 MusicXML、引擎B 出 bekern）：
- `pc` 模式：音高类级共识＋待裁＋评估
- `notes` 模式：以 B 引擎（带时值结构）为骨架，逐音符配 A 引擎佐证（✓有佐证／?待裁），产"带置信标注的骨架"

## 源分档实测结论（2026-10-10 校正）

同一曲（半页）三种源各走全链，实测分档：
- 高清印刷谱：内容级几乎全对；差异集中在连音与事件切分（记账层）。
- 视频中档源：旋律骨架可靠；内声部与节奏需逐处核；个别图处理失败（会明说）。
- 视频最低档：质量提升有限、失败风险翻倍——正确动作是换源，不硬做。

处置口径见 docs/05 分级承诺；引擎分工：骨架＝SMT（质量第一）、佐证＝homr、oemer＝高清备份位。统一入口：`tools/engine_runner.py`（图入 MusicXML 出；引擎注册表、版本注释与 run.json 留痕，备位引擎列于注册表）。
